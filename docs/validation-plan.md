# PostCheck — 制作・公開支援のチーム内比較実験

作成日：2026-11-07。状態：計画のみ、未実施。実測値はまだない。[発表方針](presentation-strategy.md)の「課題の具体性」「有効性」「UX」の根拠を得るため、既存の静止画MVPで行う予備検証。

## 確かめる問い

イベント写真と投稿文の公開準備において、手動確認に比べPostCheckを使うと、確認対象の見落としと修正漏れを減らせるか。時間・不要な加工の増加も併せて確認する。炎上減少や学習効果はこの実験の測定対象にしない。

## 準備

- 最初にチーム内の投稿担当経験を確認し、頻度・確認方法・迷った場面・困りごとを匿名で短く記録する。経験者がいなければ対象者の実証は未了と記載する。
- 架空の写真と投稿文を10〜12セット作り、同程度の難しさのA/B各5〜6セットへ分ける。対象の数・文字サイズ・写真の複雑さをなるべくそろえる。
- 両セットに連絡先、告知前の情報、確認後に残す人物・一般的な文字、修正不要の投稿を含める。実在する連絡先や未公開資料は使わない。
- 各素材に「公開不可の項目」「公開可で残す項目」「許容する対処」を事前定義する。連絡先を隠す／トリミングするなど同等の対処も認める。判定表は参加者に見せず、判断に必要な公開条件は両条件で同じように伝える。
- 素材作成者は主要な比較から除外し、参加させる場合は参考結果に分ける。人数が少なくても実数を報告する。素材数を参加者数と扱わない。
- 端末・OS・アプリ版・モデル・AI有無・登録ワード・手動編集ツール・上限時間を開始前に記録する。上限時間は練習用の別素材で決め、採点開始後に都合よく変えない。

## 比較手順

1. 採点に使わない素材で、両条件の操作を同じ程度練習する。
2. 手動条件は普段使う写真・文章編集ツールで確認・修正・書き出しを行う。PostCheck条件も同じ完了地点まで行う。手動に編集手段を与えず不利にしない。
3. 2人なら「参加者1：手動A→PostCheck B」「参加者2：PostCheck A→手動B」。4人なら「手動B→PostCheck A」「PostCheck B→手動A」も追加する。3人では割り付けが不均衡なことを記載する。同じ素材を同じ人に二度出さない。
4. 各素材は、公開条件と素材を提示した時から、修正済み写真・文章を所定の端末内保存先へ書き出すまで計時する。条件確認、AI待ち時間、再試行を含める。1セットの開始・終了条件を統一する。
5. 初回モデル導入時間は別記する。セットごとの推論初期化・待ち時間は計時に含める。設定済みの端末での評価であることを明記する。
6. 参加者は完了時に、気づいた確認対象と対処を説明する。観察担当が事前の判定表と最終出力を照合する。操作支援・失敗・時間切れも記録する。

生の投稿内容や個別AI出力のログは保存しない。記録は匿名ID、架空素材ID、件数、時間、完了状態を中心にする。共有先へ外部送信する必要はなく、保存先と出力の確認方法は両条件で固定する。

## 指標の定義

| 指標 | 定義 |
| --- | --- |
| 見落とし率 | 気づかなかった要確認項目数 / 事前定義した要確認項目数。分母0の素材は該当なし |
| 修正完了率 | 必要な修正をすべて満たし書き出せたセット数 / 全割当セット数。中断・時間切れも分母に含める |
| 不要な変更 | 公開可として残す項目を削除・マスク等した件数。文体の好みの変更などは含めない |
| 所要時間 | 公開条件・素材の提示から、修正済み写真と文章の端末内書き出しまで。時間切れは未完了として経過時間を残す |
| 不要な警告 | 事前の公開条件で確認不要とした対象へのアプリ警告数。重複警告は別の件数で記録する |
| 操作支援・エラー | 支援の有無、操作不能、AI失敗等の件数。失敗した試行を集計から除外しない |

アプリの「候補あり」だけで人が気づいたとは数えない。候補の検出性能と利用者の成果を区別する。主指標は見落とし率と修正完了率、時間と不要な変更は負担・副作用の指標として扱う。

## 余力がある場合だけ追加する検証

基本チェックのみ／Gemmaありで、同じ固定素材の候補の妥当性・追加された有用な候補・不要候補・待ち時間を比較する。これはAI追加の寄与を確かめる別実験で、人の作業成果の比較とは混ぜない。都合のよい成功例だけを選ばず、未改善例も報告する。
