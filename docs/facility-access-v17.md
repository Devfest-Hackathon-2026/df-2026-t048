# 施設の管理委任と担当者招待 V17

2026-11-09。ユーザー承認の「情報をなるべく持たず、公式窓口で確認した責任者から担当者へ権限を渡す」方針を実装。V16の管理Web統合に追加する仕様。施設ルールの内容審査と、施設を管理する権限の確認は別工程にする。

## 確認すること

「その施設の従業員である」という身分の証明ではなく、**公式窓口から、特定のログインアカウントへ管理を委任されたこと**を確認する。Googleログインや現在地だけで施設責任者とは判断しない。一般来館者のアプリは引き続きログイン不要。

1. 申請者がGoogleでログインし、施設の下書きを保存する。未確認では公開申請できない。
2. 申請一覧の施設を開いて「施設の管理権限」→「運営に責任者確認を依頼」。申請者は確認ID末尾を公式窓口の相手へ伝える。
3. 運営は上部の「責任者の確認」を開く。申請に書かれたURLだけを信じず、公式サイト・窓口を独立に確認する。URLと確認チェックから確認リンクを発行する。
4. **運営がその公式窓口へリンクを手動で送る。申請者にリンクを渡さない。** メールアドレス・電話番号の入力・DB保存、自動メール配信は行わない。
5. 公式窓口の相手が、施設名と委任先の確認ID末尾を照合し、リンクの「管理を委任する」を押す。公式窓口側のGoogleログインは不要。権限はリンクを開いた人ではなく、確認依頼に固定されたアカウントへ付与する。
6. 責任者は管理画面で再読み込みし、ルールを申請する。運営が根拠・公開内容を審査して承認した版だけ、アプリへ配信する。

公式窓口・確認IDの照合は人の運用に依存する。リンクの転送・公式メールの乗っ取り・誤った窓口認定まで防げると説明しない。DNSや公式サイトへの確認コード設置による自動認証は今回実装しない。

## 役割と操作

| 役割 | 施設の下書き・閲覧 | 公開申請 | 招待・解除 | ルール承認・停止 |
| --- | --- | --- | --- | --- |
| 未確認の作成者 | 自分の未確認施設のみ | 不可 | 不可 | 不可 |
| 担当者 editor | 招待された施設のみ | 可 | 不可 | 不可 |
| 施設責任者 manager | 確認・招待された施設のみ | 可 | 同じ施設のみ | 不可 |
| 運営 operator | 審査・公開版の確認。未申請の下書き全文は非表示 | 不可 | 初回・再確認リンクの発行 | 可。自己の申請承認は不可 |
| 一般利用者 | 承認・公開された有効版のみ | 不可 | 不可 | 不可 |

同じ組織IDだけでは編集権限を与えない。確認済み施設の作成者も、失効・解除後は編集できない。旧版で審査待ちの申請は、申請者が一度取り下げ、責任者確認後に再申請する。旧データの組織IDが作成者UIDと一致しない場合は自動で権限を引き継がず、運営が確認して移行する必要がある。公開申請時と運営の承認時に、提出アカウントの有効な施設権限をAPIで再確認する。承認待ちに権限が失効した場合は再確認・再申請が必要。

## 招待・引き継ぎ・期限

- 責任者が「施設の管理権限」から担当者／別の責任者の招待リンクを発行し、相手へ直接共有する。招待先のメールアドレスや氏名は登録しない。
- 相手は自分のGoogleアカウントでログインし、明示的に招待を受ける。リンクを知っているだけでは担当者にならない。
- 確認／招待リンクは24時間、一度限り。ランダム32バイトの値を使い、サーバーにはSHA-256ハッシュだけ保存。使用・権限付与は同じCAS書き込みで確定する。
- 確認リンクの再発行で、その確認依頼の古いリンクを無効にする。招待リンクは独立に発行する。発行責任者の解除で、その人が発行した未使用招待も削除する。
- 施設の権限は最長90日。招待の権限・リンク期限は発行者の権限期限を超えない。既に受け付けた他のメンバーの権限は、発行者の解除だけでは連鎖解除しない。必要なメンバーを個別に解除する。
- 最後の有効な責任者は解除できない。別の責任者を招待してから引き継ぐ。期限更新は公式窓口での再確認。
- 権限失効で施設が一覧から消えた場合は、上部の「確認依頼」から施設IDで再確認を依頼する。元の作成者、または公開版がある施設に対する依頼を受け付ける。それ以外の非公開施設は運営と個別調整が必要。
- 24時間／90日は試作の設計値であり、実測値や大会の要件ではない。

## 保存する情報と保存しない情報

| 保存先 | 内容 |
| --- | --- |
| 施設レジストリ（既存Firestore＋Cloud KMS暗号化） | 施設の公開ルール・審査用根拠、施設ID、作成・提出UID、初回確認日時 |
| 同レジストリの管理情報 | UIDと施設ID、役割、確認・有効期限、確認依頼の状態・日時、運営が確認した公式サイトURL、未使用リンクのハッシュ・種別・期限・発行UID |
| 操作記録 | 施設ID、操作UID、操作種別、日時。既存と合わせ最大500件 |
| Firebase Authentication | GoogleログインのUID・メール・表示名など、認証基盤が保持するプロフィール |

管理Webから担当者の氏名・電話・メール専用欄を削除した。旧クライアントが`contact`を送っても破棄する。サーバー起動時とレジストリ更新時に、既存の下書き・公開スナップショットの専用`contact`値を除去する。施設ルール自体は残す。

これは**個人情報ゼロのシステムではない**。UIDもアカウントを識別する情報であり、Firebase Authや手動連絡に使うメールサービスには情報が残る。公式サイトURL・根拠原文・参考画像などの自由入力に個人情報を書かない運用が必要。専用欄の削除は、過去のバックアップ・監査ログ・メールや自由入力中の情報まで消したことを意味しない。本人情報を消すアカウント削除・保存期間の自動運用は後続。

写真・投稿文・OCR・個人の登録ワードをクラウドAIへ送らない既存方針は継続。個人設定のクラウド復元・Appleログインは有効化しない。

## APIと分離

権限ロジックはGoの`cloud/internal/rules/access.go`。HTTPは`ruleapi/access.go`、暗号化保存とFirebase IDトークン検証は既存Googleアダプター、Webは`admin_web/lib/access_page.dart`。共有Dartの`RulesApi`から接続する。

| API | 利用者 |
| --- | --- |
| GET/POST `/v1/access/requests` | 自分の確認依頼を取得／作成。運営は全依頼を取得 |
| GET `/v1/access/venues/{id}` | 対象施設の有効な担当者・責任者、未確認の作成者 |
| POST `/v1/access/requests/{id}/issue` | 運営のみ。公式URLと確認チェック必須 |
| POST `/v1/access/venues/{id}/invite` | 対象施設の責任者のみ |
| POST `/v1/access/venues/{id}/revoke` | 対象施設の責任者のみ |
| POST `/v1/access/preview` | リンク所有者。最小限の施設名・役割・委任先ID末尾のみ |
| POST `/v1/access/consume` | 確認リンクは匿名可、招待リンクは本人ログイン必須 |

リンク値はURLフラグメントに入れ、起動直後にアドレスバーから取り除く。APIへはJSONの本文で送り、アクセスURLやアプリのログに生値を出さない。APIはno-store、Hostingはno-referrer。リンクは記録・スクリーンショット・Gitに含めない。

既存の単一暗号化レジストリを利用する試作で、施設100・確認依頼500・未使用リンク500・メンバー1000・レジストリ700KBの上限がある。期限切れリンク／メンバーの整理は書き込み時で、定期TTL処理ではない。確認依頼の自動削除・取消、専用のレート制限、自動メール配信、大規模な施設管理向けのDB分割は後続。
