# PostCheck — クリエイティブカテゴリでの発表・評価方針

更新日：2026-11-07。ユーザーの指示によりクリエイティブカテゴリで進める。これは出場方針の決定であり、運営による適合承認ではない。実装状況は[roadmap.md](roadmap.md)、公式基準は[大会ルール](../hackathon-rules.md)を参照する。

## 伝える価値

**PostCheck — 写真と投稿文を、確認・修正して共有へ。**

> SNSでイベントや活動を発信する人に向けた、投稿素材の制作・公開支援アプリです。写真の写り込みや投稿文の確認候補を端末内で示し、利用者が必要な部分を隠す・直す・そのまま使うと判断して、書き出しまで進めます。

炎上・情報漏えい対策という目的は維持する。説明は「炎上を予測する」ではなく、実際に扱う制作工程と見落としへの対処を中心にする。カテゴリ名に合わせて機能や実績を言い換えて水増ししない。

最初の対象は、サークル・学生団体などでイベント写真と投稿文を作るSNS担当者に絞って検証する。これは開発上の対象仮説であり、需要確認済みという意味ではない。チームの実体験がこの対象に当てはまるか、最初に確認する。

## 課題からデモまでの一貫した場面

1. イベントの様子を写真と文章で伝えたい。
2. 主役や文章に注意が向き、背景の連絡先や未公開情報を見落とす可能性がある。
3. PostCheckが対象箇所と短い確認理由を示す。
4. 利用者が必要な部分だけ修正し、公開可能と設定された内容は残す。
5. 修正した写真と文章を再確認し、書き出してOSの共有先選択へ進む。

架空のイベントを使い、連絡先は掲載不可、イベント名と同意取得済みの登壇者は公開可、次回企画は告知前、という条件を先に定める。AIが同意・機密性を自動で知っているとは説明しない。条件は実験参加者・デモ視聴者へ伝え、アプリが実際に受け取った入力や登録ワードと区別する。

制作支援として、必要な修正ができることと、残すべき内容を不要に消さないことを両方示す。ライブ警告は未実装のため、現在のデモは撮影後または写真選択後の確認から開始する。ライブが検証できた場合だけ実演へ追加する。

公式は各0〜3点・計24点で、詳細な点数別条件は未提示。下表は得点保証や独自の公式基準ではなく、説明と証拠をそろえるための作業表。

| 審査項目 | 示す内容 | 必要な証拠・残件 |

| Google技術が中核で有効 | ML Kitの位置情報、Gemma / LiteRT-LMの文脈補助が確認・修正につながる | 実機の一連デモ。Gemma固有の寄与は基本チェックとの比較が未実施 |
| 選定理由の具体性 | 端末内処理の要件、位置検出と文脈解析の分担、Flutterとポートの役割 | 下記の採用・不採用比較。容量・待ち時間・誤候補も説明 |
| 一連の完成度 | 入力→確認→判断→修正→再確認→書き出し | 同じ架空素材の実機記録。中断・失敗時の復帰も確認 |

| 安全性・拡張性・保守性 | 端末内解析、人の判断、出力検証、SDKと中核処理の分離 | 現行ソースと対応テスト。SNS別アダプターは将来案と明記 |

| ピッチ・説明力 | 課題→一連の実演→実測→技術選定の順でつながる | 下記台本、同じ素材の修正前後、短い結果表。専門語の列挙を避ける |

## 技術選定の説明メモ

| 選択 | 理由 | 比較対象・引き受ける欠点 |
| --- | --- | --- |
| 端末内のGemma / LiteRT-LM | 投稿内容をクラウドAIへ送らず文脈確認を補助する | クラウド推論は現行のデータ方針に合わない。端末ではモデル導入・容量・待ち時間・対応機種が制約 |
| ML Kit + ルール + 文脈補助 | 文字・位置と、文脈に関する確認候補を分担する | ルールのみでも基本チェックは可能。Gemma追加の効果は未検証で、比較して説明する |
| 利用者が隠す・残すを判断 | 公開条件や掲載同意は画像だけで確定できない | 自動一括マスクより操作は増える。不要な加工と確認負担を実験で測る |
| Flutter + SDK境界の分離 | 入出力・画面とチェック処理を分離し、接続変更の影響を限定する | ブリッジはコミュニティ製を含む。複数OS・SNSでの実用性は未検証 |

比較表は現在の設計理由の整理。過去に実施していない比較試験や議論を「実施した」と説明しない。公式テーマの Own the Why に合わせ、今後の変更時は選択・代替案・根拠・制約を追記する。詳しい技術根拠は[技術レビュー](google-tech-review.md)を参照。

## 発表台本の骨子

2026-11-09にユーザーから「発表4分＋質疑応答1分半」と共有されたため、今回はこちらを優先する。本編7枚を3分40秒で進め、4分まで20秒を操作待ち・言い直しの余裕とする。以下は配分案であり、通しリハーサルの実測ではない。

| 本編 | 時刻 | 配分 |
| --- | --- | --- |
| 1：課題とPostCheck | 0:00–0:15 | 15秒 |
| 2：テーマへの回答・採用理由 | 0:15–0:40 | 25秒 |
| 3：写真・投稿文の実演 | 0:40–2:20 | 100秒、端末切替と復帰込み |
| 4：縦横2軸の競合マトリクス | 2:20–2:40 | 20秒 |
| 5：現在地と施設ルール | 2:40–3:05 | 25秒 |
| 6：全体アーキテクチャと入力層・DB分離 | 3:05–3:35 | 30秒 |
| 7：締め | 3:35–3:40 | 5秒 |

テーマ・競合マトリクス・位置情報による施設ルール適用・アーキテクチャ図は本編に残す。実演は架空素材1セットに絞り、連絡先を隠す／掲載できる内容を残す／投稿文を直す／仕上がり・共有先を確認する。実際の投稿や施設管理Webの追加実演は行わない。2:10を過ぎたら新しい操作を始めず、2:20までにスライドへ復帰する。

同じ端末・版・素材・設定で事前に通し練習する。実演が10秒以上進まなければ非表示の補足1を手動で開き、静止画と明示して15秒程度で説明し、本編4へ戻る。比較実験は未測定のため、効果の実績スライドは追加しない。

質疑90秒は本編と分ける。回答はまず一文で、必要に応じて20〜30秒の補足を行う。5枚の補足は通常のスライドショーでは非表示にし、入力・DB分離、採用案と代替案、検証範囲を聞かれた場合だけ手動で表示する。独自開発は既存の照合・撮影時スナップショット・確認修正の実装を説明し、Issue #44の強化内容やOSS公開を完了済みとして話さない。

改訂資料：`output/postcheck-pitch-v8/deliverables/PostCheck-pitch-v8-4min.pptx`。各スライドの発表者ノートに短い台詞・通過時刻・質疑用の回答例を収録する。

冒頭案：

> イベントの楽しさを伝える一枚でも、背景の連絡先まで公開するつもりはありません。PostCheckは、写真と投稿文の気になる箇所を端末内で示し、必要な部分を直して共有するまでを支援します。

## 次の順序

1. 対象者の投稿担当経験を確認し、実際の困りごとを短く記録する。
2. 架空素材・判定基準・実験条件を固定する。
3. 既存の静止画MVPで比較実験を行い、結果を記入する。
4. 完了を妨げた不具合や操作を優先して改善し、変更後の結果は別の版として記録する。
5. 同じ制作場面でデモ・結果・技術選定の説明をそろえる。大会条件の未対応事項は並行して解消する。

教育機能・意味検索モデル・複数SNS連携の追加を採点対策の必須作業にはしない。ライブの既存要件案は維持するが、実験開始をライブ実装完了まで待たせない。
