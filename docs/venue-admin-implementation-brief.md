# 施設ルール：申請者画面・運営画面の実装仕様（90分）

更新：2026-11-08。対象は既存のFlutter Web管理画面とGo API。これはチームメンバー向けの作業仕様であり、本番運用の完成を意味しない。

2026-11-09追記：iwaseのUIと既存APIを統合・配置済み。最新の差分・検証は[統合記録V16](admin-integration-v16.md)。申請名・審査用参考画像を追加し、公式サイトと有効期限は任意、根拠原文と参考URLまたは参考画像を申請時必須とした。参考画像と連絡先はアプリへ配信しない。下記は当初の依頼時点の仕様・課題。

## 目的

施設の担当者が、撮影・SNS公開に関するルールと根拠を申請する。運営は申請者とは別の立場で根拠を確認し、承認された内容だけをアプリに配信する。施設で撮影する人が、その場のルールに気づけるようにする。

同じ管理画面URLを使用し、Googleログイン後にサーバーが返す権限で画面を切り替える。見た目だけでなく、API側でも許可・拒否を強制する。今回、アプリ本体の写真解析や位置情報の仕組みは変更しない。

## 利用者と権限

| 操作 | 申請者 | 運営 |
| --- | --- | --- |
| 自組織の施設を作成・下書き・編集・申請・取り下げ | 可 | 運営画面からは行わない |
| 他組織の下書き・申請を見る | 不可 | 審査のため可 |
| 他組織の下書き・申請を変更・申請・取り下げ | 不可 | **不可に修正する** |
| 申請を承認・理由付き差し戻し | 不可 | 可。ただし自組織の申請は不可 |
| 公開停止 | 不可 | 理由付きで可 |
| 公開済みルールを取得 | アプリ利用者はログイン不要 | 同左 |

現在は一般のGoogleログイン利用者が、本人用の組織枠で申請可能。組織の所属・施設管理権限の確認は運営が行う。新しい人が同じ組織に参加する仕組み、招待制、本人性の自動審査は今回の対象外。ログインだけで既存組織へ所属させない。

重要：現在のAPIは `allowed()` により運営が他組織の下書きを変更できる。UIでボタンが隠れていてもAPI直叩きで可能なので、操作ごとの認可をサーバーで修正する。運営が他組織の下書きを変更・代理申請し、その申請を承認できる抜け道も塞ぐ。運営が申請者の所属を自分で切り替えられる機能は追加しない。

## 申請者画面：やりたいこと

1. Googleでログインし、自分の施設一覧を見る。状態は「下書き／審査中／差し戻し／公開中／公開停止」が分かる。
2. 「施設を登録」から施設名、住所、位置（緯度・経度）、公式サイト、担当者の連絡先を入力する。現状、Webの地図キーは未設定のため座標入力を使う。Places APIは使わない。
3. 撮影・SNS公開・商用利用の条件、必要な確認ワード、対象エリア、根拠URL・原文、公開範囲を入力する。日時は任意。申請時には住所、公式サイト（HTTPS）、連絡先、根拠URL（HTTPS）、根拠の原文を必須にする。
4. 内容と、一般公開するワードが端末へ配信されることを確認して申請する。担当者の連絡先は公開しない。申請中の版は編集させず、取り下げてから変更する。
5. 保存・通信・申請で失敗した場合は入力を保持し、どの項目が不足・不正か明示する。申請成功はAPIの成功を受け取ってから表示する。二重クリックによる重複施設・重複申請を防ぐ。

**いまの実障害**：実クラウドで架空施設は暗号化して下書き保存できたが、申請はHTTP 400。保存版の住所・連絡先・公式サイト・根拠URLが空で、画面上で原因が分かりにくかった。なぜ入力が保存版に反映されなかったかは未確定。複数ステップをまたぐ入力・下書き保存・再編集・申請を再現し、値の保持とサーバー検証の両方を調べる。原因を決めつけてはいけない。

## 運営画面：やりたいこと

1. 運営権限を持つGoogleアカウントでログインし、すべての申請・施設を一覧で見る。少なくとも「審査中」「公開中」「差し戻し」を見分ける。
2. 申請詳細で施設名・位置・住所・連絡先・公式サイト、撮影／公開条件、確認ワード、根拠URL・原文、公開範囲を確認する。公開中の版がある場合は申請内容と区別する。
3. 施設との関係、根拠、公開対象を確認して承認。問題があれば理由を付けて差し戻す。公開中の内容には理由を付けて公開停止できる。
4. 承認するまで公開中の旧版を維持し、承認・差し戻し・公開停止はサーバーの権限確認とバージョン競合確認を通す。

今回の画面は「組織から受け取った申請を審査する場所」。運営による施設の代理登録、変更や代理申請は対象外。アプリでの施設の表示・手動選択・近接適用は承認された公開版を使う。

## 状態遷移

```text
下書き → 申請中 → 承認・公開中
             ├→ 差し戻し → 下書きの修正 → 再申請
             └→ 申請者が取り下げ → 下書き
公開中 → 新版を下書き・申請 → 承認まで旧版を公開
公開中 → 運営が理由付きで公開停止
```

保存済み下書きが申請中と誤認されないこと。エラー発生時は実際の保存状態を正直に表示し、二重登録せず再試行できること。

## 90分の優先順位

| 目安 | 作業 | 完了の目安 |
| --- | --- | --- |
| 0〜15分 | 既存の動線・ローカルデモとテストを確認。入力保持の障害を再現 | 申請が失敗する手順または失敗箇所を特定 |
| 15〜45分 | 申請フォームの値保持と必須項目の検証・エラー表示を修正 | 入力→画面遷移→保存→申請で値が失われず、未入力箇所が分かる |
| 45〜70分 | Go APIの操作別権限を修正 | 申請者は他組織を変更できず、運営も他組織の下書き変更・代理申請ができない |
| 70〜90分 | 架空データで主要フローと失敗ケースを確認 | 以下の受け入れ条件を記録し、未検証は明示 |

時間が足りなければ、権限の抜け道を残したまま完了とせず、対応できた範囲と残タスクを共有する。UIの大幅リニューアル、招待制、場所検索、PDF取込、動画、クラウド復元はこの90分に含めない。

## 受け入れ条件

- [ ] 2つの別アカウントで申請者／運営の画面を区別でき、権限はクライアントの表示ではなくサーバーが決定する。
- [ ] 架空データで入力→下書き→再編集→申請。全項目が保持され、不足があれば項目名を表示して入力を失わない。
- [ ] 未ログインの管理操作、申請者の他組織操作・承認、運営の他組織の下書き変更・申請・取り下げ、自組織の承認はAPIで拒否される。
- [ ] 運営が別組織の申請を承認でき、一般公開APIが承認済み版だけを返す。公開応答に担当者連絡先は含まれない。
- [ ] 差し戻しと公開停止には理由が必要。版の不一致時は競合として失敗し、入力は失われない。
- [ ] テストでは架空の施設・連絡先のみ使用し、既存のデータや本物の施設には触れない。公開テストを行う場合は架空データと明示し、終了後に公開停止する。
- [ ] 対象テストを実行し、結果と実クラウド・iPhoneで未確認の項目を区別して共有する。
