# OCR前処理＋Gemma調整の実装記録

更新：2026-11-09。[統合設計](ocr-gemma-combined-design.md)に基づく撮影後チェックの変更。今回の実装を精度改善の実測結果として扱わない。

## 実装した内容

### OCRと画像処理

- 基本解析（日本語／Latin OCR・顔・画面）の結果を段階ごとに保持する`ProgressivePerceptionPort`を追加。従来の`PerceptionPort`実装も引き続き利用可能。
- 基本解析後にガンマ補正（指数`1/1.4`）と2×2タイルを逐次実行。タイルは隣接方向で元画像幅・高さの7.5%を共有し、各半分の長さに対して15%のオーバーラップ。拡大最大2倍、目標長辺1600px、縮小なし。
- 追加画像は1枚ずつ別isolateで生成し、各画像で日本語→Latinを実行する。通常2回＋ガンマ2回＋タイル8回でOCRは最大12回。顔・画面は各1回のみ。
- タイル内の座標は、実際のリサイズ後寸法と切出し領域からA入力の正規化座標に戻す。
- 作業用ディレクトリの初回作成、変換画像のメタデータ除去、ネイティブ処理終了後の削除を実装。
- 元画像は従来どおり長辺2400px。縮小前画像を保持する高解像度経路、deskew、二値化は実装対象外。

### 時間制限と実行中の資源

- 基本＋追加の写真解析は45秒。基本完了から追加は最大10秒。いずれも待機期限であり、SDKを強制停止できるという意味ではない。
- 各部分結果は不変のスナップショットで保持。時間切れ・例外でも投稿文と取得済み観測のルール結果を返す。
- 基本解析完了後／AI待機中に「現在の結果で確認する」を表示し、結果を確定できる。
- キャンセル／確定後は次の呼出しを開始せず、遅延結果は反映しない。実行中SDKの所有者が完了後にcloseとファイル削除を行う。
- 共通の`AnalysisGate`でML KitとGemmaの重い処理の重複を防ぐ。期限後もSDKが動いていればGemmaを省略し、次のチェックも基本の文章結果・目視確認へ進む。
- Gemmaは別枠90秒。チェック全体45秒という仕様ではない。

### 読取候補と確認画面

- `OcrReading`に文字列・矩形・パス・タイルIDを保持。同じ行の代替読取は`TextBlock.readings`に保持する。
- 同文言のIoU 0.65以上、別文言のIoU 0.8以上、または同一行の包含率0.9以上＋文字列包含を初期基準とする。行の高さ比1.6以内・縦方向の重なり0.75以上も必要。候補が複数グループに一致する曖昧な場合は別項目にする。
- 別の読取候補で連絡先／登録ワードが成立した場合も判定を維持する。部分行を推測で連結しない。
- 明示的に同じOCRグループを指すルール判定とGemmaの指摘は、1つの`Finding`に関連根拠を付けて統合する。独立した`ReviewItem`クラスを増やす代わりに、既存の選択・マスクの契約を保つ実装とした。
- 根拠の質問・別読取・施設原文は選択項目内に表示する。企業モードの必須マスクは、代表の種類だけでなく関連根拠の種類にも適用する。
- 位置不明のGemma指摘は写真全体の確認項目として残し、「範囲を指定して隠す」へつなぐ。自動で写真全体を塗りつぶさない。

### Gemma

- `visual-review-v2`の指示で、OCRが不完全でも写真を直接確認し、名札・資料・画面等について根拠のある短い質問を促す。読めない内容・身元・同意・機密性の推測や座標生成は禁止。
- 画像を先に、JSON化した投稿文・OCRを後に渡す。モデル・GPU/CPU設定・サンプリングは既存を維持する。
- 連絡先／登録ワードのグループを優先して入力し、残りを画像上の位置順で補う。最大32読取・各180文字、OCR合計1600 UTF-16コード単位、投稿文3000コード単位。サロゲートペアを分断しない。
- 合計1600の上限は追加した入力量の制限であり、4096トークン内を厳密に保証するトークナイザ計測ではない。実機の長文・文字量が多い写真での調整が必要。省略を入力と画面に明示する。
- Gemmaへ実際に送ったID・投稿文の範囲を保存し、未知ID、未送信ID、範囲外引用、複数参照、同じ引用が元の投稿文で複数箇所に現れる回答、座標等の未知フィールドを棄却する。
- 追加学習・LoRA・soft prompt学習・回答例の追加は行っていない。まず指示文の調整を独立評価する。
- 生の写真・OCR・投稿文・個別AI出力をログへ出す処理は追加していない。

## 検証と比較の再現方法

自動テストは、画像変換・メタデータ除去・EXIF向き・座標・読取統合・根拠保持・企業ルール・AI参照検証・時間切れ・遅延SDKエラー・キャンセル・日英の小画面での操作を対象にする。結果は下記「実行結果」に記録する。

実機用には`integration_test/ocr_gemma_combined_device_test.dart`を追加した。アプリ内で生成する架空サンプル1枚に対し、A：通常OCR＋旧指示、B：追加OCR＋旧指示、C：通常OCR＋新指示、D：追加OCR＋新指示を実行する。モデルが実際に成功すること、連絡先候補、対象の有効性、資源の解放を検証する。

これは4経路のスモークテストであり、48枚の正解付き評価・p95・意味的な見逃し率の比較を代替しない。端末出力は条件ごとの時間・候補数等の集計だけとし、モデルの個別出力は出さない。

```sh
# postcheck/から、通常のFlutter検証を実行
flutter analyze --no-pub
flutter test --no-pub

# 同期フォルダの外へstage_build.shで配置後、接続中のiPhoneで実行
flutter drive --profile --driver=test_driver/integration_test.dart \
  --target=integration_test/ocr_gemma_combined_device_test.dart -d DEVICE_UDID \
  --dart-define-from-file=config/rules.local.json
```

通常アプリの内部比較スイッチは`--dart-define=POSTCHECK_OCR_ENHANCED=false`、`--dart-define=POSTCHECK_CONTEXT_V2=false`。既定はいずれもtrue。設定画面には追加しない。同じ実行中に4条件を比較する場合は、実機テストのコンストラクタ引数を使う。

## 残る検証

- 固定した正解付き48枚セットでの調整用／評価用分割、4条件比較、見逃し・不要指摘・誤統合・マスク被覆の計測。
- 待ち時間、不要指摘、メモリの許容上限の確定と受入判定。今回の初期上限値を実測値と扱わない。
- 長文・大量OCRの入力予算、連続利用時のメモリ・電池、低性能端末、Android実機。
- 高解像度タイルが必要かの判断。
