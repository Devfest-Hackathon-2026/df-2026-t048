---

## 1. 一言でいうと

撮影後の文字チェックは、いま **Google ML Kit の文字認識（端末内）が読めた行だけ** を確認候補にしている。  
細い字・小さい字・斜め・薄暗いで見逃しやすいのは、**OCR前に画像を読みやすくする処理が無い**ことが主因候補である。

本提案では **ライブOCRは変更しない**。  
**撮影後パスだけ**に、原画像OCRを残したまま「前処理つき再認識」を追加し、結果をマージする。

---

## 2. 現状（実装事実）

### 2.1 処理の流れ（撮影後）

```text
利用者が選んだ／撮った写真
  → prepareRaster（向き補正、長辺が2400px超なら縮小、JPEG quality 95、EXIF除去）
  → MlKitPerceptionAdapter.inspect
       1) TextRecognizer(japanese)
       2) TextRecognizer(latin)
  → 認識結果の「行（line）」を TextBlock として収集（重複は近い矩形かつ同一文言なら除外）
  → RuleChecker が確認候補へ変換
       - 電話・メールらしき文字列 → 連絡先
       - 登録ワード／施設ワード → 登録ワード
       - それ以外の読めた文字 → 写り込んだ文字
  →（任意）端末内 Gemma が文脈候補を追加
```

重要な制約：

- 写真・投稿文・OCR結果はクラウドAIへ送らない（プロダクト方針）。
- ML Kit が返さなかった文字は、アプリ上に検出結果として存在しない。
- Gemma は既存OCR結果を前提にし、読めなかった領域を新たに「発見」しない。
- ライブ撮影中のOCR（`live_camera_page.dart`）は別経路。**本提案では触らない。**

### 2.2 いまやっていないこと

撮影後OCRの直前に、次の処理は **未実装**：

| 未実装の前処理 | 狙いだったこと |
| --- | --- |
| コントラスト強調 | 薄暗い・低コントラスト文字を読みやすくする |
| 二値化 | 細い字・背景との差が弱い字を強調する |
| 傾き補正（deskew） | 斜めに写った文字を水平に近づける |
| 拡大クロップ／タイル分割再認識 | 小さい字の1文字あたり像素を増やす |

いまの前処理に近いのは、向き補正と長辺2400px制限のみ。

### 2.3 弱い条件と現状の関係

| 条件 | 現状との関係 |
| --- | --- |
| 細い字・小さい字 | Googleはおおよそ1文字16×16px以上を目安とする。距離・縮小で下回りやすい。拡大再認識なし |
| 斜め | 専用deskewなし。ML Kit任せ |
| 薄暗い | 明るさ・コントラスト補正なし |
| （参考）ライブ | 解像度低め・間引き・片スクリプト交互。**今回の改善対象外** |

参考：[ML Kit Text Recognition（iOS）](https://developers.google.com/ml-kit/vision/text-recognition/v2/ios)

## 3. 目標

### 3.1 達成したいこと

1. 撮影後チェックで、細い／小さい／斜め／薄暗い文字の **見逃しを減らす**。
2. 特に連絡先らしい文字列（電話・メール）の見逃し低減を優先する。
3. 既存の確認UX（候補提示、利用者が最終判断）を維持する。
4. 端末内処理・非クラウド方針を維持する。

### 3.2 達成したことにしないこと

- 「すべての文字を読める」ことの保証
- 炎上・漏えいが起きないことの保証
- ライブ警告の精度改善（対象外）
- クラウドモデルによる読み取り補完

## 4. 提案する仕組み

### 4.1 基本方針

**原画像でのOCR（現行）は残す。**  
そのうえで、前処理した画像でもOCRし、行単位の結果をマージする。

```text
[パスA] 原画像（現行どおり）
[パスB] コントラスト強調画像
[パスC] タイル分割→各タイルを拡大→OCR→座標を元画像へ戻す
（後続候補）傾き補正パス、条件付き二値化パス

        ↓
   行単位でマージ・重複整理
        ↓
   既存 RuleChecker / 確認UI
```

理由：

- 前処理は効く条件と壊す条件がある。原画像パスを消すと、今読めていた文字を落とす危険がある。
- 「追加で読めた行」だけを足す方が安全に始められる。

### 4.2 パス詳細

#### パスA：原画像（必須・現行）

現行の `prepareRaster` 後画像を、日本語OCR→ラテンOCRする。ベースライン。

#### パスB：コントラスト強調（Phase 1で実装）

- 目的：薄暗い、コントラストが低い文字。
- 手法候補：CLAHE相当、またはヒストグラム／ガンマ補正。最初は1手法に固定して測る。
- 出力：強調後画像をパスAと同じOCR手順で処理。
- 注意：ノイズが増えて誤検出が増える可能性がある。

#### パスC：タイル拡大（Phase 1で実装）

- 目的：細い字・小さい字（16×16px目安を下回るケース）。
- 手順：
  1. 画像を格子状に分割（初期案：2×2、オーバーラップ10〜15%）。
  2. 各タイルを拡大（初期案：タイル長辺を1280〜1600px程度へ）。
  3. タイルごとに日本語→ラテンOCR。
  4. 検出矩形を元画像座標へ変換。
- 上限：タイル数・拡大率に上限を置き、処理時間を抑える。
- 注意：時間増が最大のリスク。撮影後のみ適用。

#### パスD：傾き補正（Phase 2・計測後）

- 目的：斜め文字。
- 手順案：角度推定 → 閾値を超えるときだけ回転 → OCR → 矩形を逆回転して元座標へ。
- 初期は常時実行しない。Phase 0の斜めセットで効果が出てから入れる。

#### パスE：二値化（Phase 2・計測後・条件付き）

- 目的：細い字の補助。
- 全面常時は推奨しない（背景写真を壊しやすい）。
- パスA/B/Cで候補が少ない領域に限定するなどを条件にする。

### 4.3 マージ規則

1. 単位は現行どおり **行（line）**。
2. 文言が同一（大文字小文字無視）かつ矩形の重なりが大きいものは1つにまとめる。
3. 文言が違う場合は残す（誤った統合で連絡先判定を落とさない）。
4. 座標はすべて **元画像（パスA入力）座標系** に揃えてからUIへ渡す。
5. RuleCheckerの分類ロジックは変更しない（電話・メール正規表現、登録ワード照合は現状維持）。

### 4.4 アーキテクチャ上の置き場所

| 層 | 方針 |
| --- | --- |
| `domain` / `application` | RuleCheckerは原則そのまま。必要ならマージ用の純関数をapplicationまたはadapters隣に置く |
| `adapters/image_processing.dart` | コントラスト・タイル・回転などの画像変換 |
| `adapters/mlkit_perception.dart` | 複数パスOCRの実行と結果統合 |
| `presentation` | 進捗表示の文言調整のみ（ライブUI変更はしない） |

SDK型（ML Kit）はadaptersに閉じる。domainがML Kitを参照しない現行方針を維持する。

---

## 5. 対象外（明確にやらない）

次は本提案のスコープ外である。別提案が必要。

1. **ライブOCRの強化**（ガイド追加、ROI OCR、高解像度スナップ、フレーム間隔変更など）
2. クラウドOCR・クラウド画像理解
3. 「読めなかった文字」を生成AIに推測させて検出扱いすること
4. 画面検出・顔検出の精度改善
5. ぼかし／マスク編集そのものの変更（OCR改善の直接対象ではない）

## 6. 進め方

### Phase 0：計測（実装前）

架空データのみを使う（実在の個人情報を使わない）。

用意する条件例：

- 文字サイズ：大／中／小（画像上の1文字pxを記録）
- 傾き：0°／15°／30°
- 照明：明るい／薄暗い
- 書体：通常／細い

測る指標：

| 指標 | 意味 |
| --- | --- |
| 見逃し率 | 正解文字のうち、候補に出なかった割合。連絡先相当を別集計 |
| 誤検出数 | 文字がない／無関係な箇所を候補にした数 |
| 位置ずれ | 枠が文字からどれだけずれるか |
| 処理時間 | 中央値とp95。既存の45秒タイムアウト内か |

ベースラインは **現行の単一パスML Kit**。

### Phase 1：最初の実装スコープ（推奨）

実装する：

1. パスA（現行）維持
2. パスB（コントラスト強調）追加
3. パスC（2×2タイル拡大）追加
4. マージ
5. Phase 0同一素材での再計測メモ

実装しない（このPhase）：

- deskew
- 二値化
- ライブ変更

### Phase 2：計測結果を見て追加

- 斜めセットで効果があれば deskew
- 細い字でなお不足なら条件付き二値化
- タイル数・拡大率の調整

---

## 7. 受入条件（Phase 1）

すべて満たしたら Phase 1 完了とする。

1. 写真・OCRがクラウドに送信されない。
2. ライブOCRのコード経路を、精度改善目的で変更していない。
3. 原画像パスが残っており、前処理パスは追加である。
4. Phase 0と同一の評価セットで、次のいずれか以上を改善している（数値は計測後に記録）：
   - 小さい文字の見逃し
   - 薄暗い条件の見逃し
5. 連絡先相当の見逃しがベースラインより悪化していない。
6. 誤検出の増加が、事前に決めた上限以内。
7. 撮影後チェックが既存タイムアウト（45秒）内で完了するケースが主である（p95を記録）。
8. 認識できない場合でも、目視確認・手動範囲指定の手段が残っている。
9. 自動テスト（前処理・座標変換・マージ）と、架空データでの実機確認記録がある。

## 8. リスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 処理時間増 | 待ち時間が長い、タイムアウト | タイル上限、パス数固定、時間計測、進捗表示 |
| 誤検出増 | 不要な確認が増える | 原画像結果との突合、マージ規則、評価で上限管理 |
| 座標変換ミス | 枠がずれる | 単体テスト＋実機オーバーレイ確認 |
| 前処理が逆効果 | 今読めていた字を落とす | 原画像パス必須 |
| 効果の過大説明 | 利用者・発表での誤解 | 「確認候補の改善」であり検出保証ではないと明記 |

## 9. 作業時の読み方（人／AI向け）

実装やレビューをするとき、次を前提にしてよい。

1. 触ってよい主ファイルは撮影後経路（`mlkit_perception.dart` / `image_processing.dart`）。
2. `live_camera_page.dart` のOCR強化はこの提案の成果物に含めない。
3. まず「原画像 + コントラスト + 2×2タイル拡大 + マージ」まで。
4. deskew・二値化は Phase 0/1 の数字を見てから。
5. 実在個人情報や本番投稿内容で精度評価しない。
6. 完了報告では、見逃し・誤検出・処理時間をベースライン比較で書く。ローカル成功だけを実機成功と書かない。

## 10. 意思決定済み／未決

### 決定済み

- ライブ強化は行わない。
- 撮影後の前処理つき再認識（原画像維持＋追加パス）で進める。
- 最初の実装はコントラスト強調とタイル拡大を中心にする。

### 未決（実装前に決める）

1. Phase 1の処理時間の許容上限（体感秒数、またはp95の目標）。
2. 評価セットの枚数・作成担当。
3. 誤検出増加の許容上限（例：ベースライン比＋N件まで）。
